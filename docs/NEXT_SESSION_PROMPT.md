# برومت المتابعة — إكمال PROMANGO وإطلاقه للعامة

> **كيف يُستعمل:** انسخ كل ما تحت الخط في بداية جلسة جديدة (Claude Code) مع إرفاق مجلد المشروع (`PROMANGO/`). كل شيء فيه مُتحقَّق منه بتاريخ **2026-11-19**؛ ما لم يُتحقَّق منه مذكور صراحة.

---

## 0. دورك والهدف

أنت المنفّذ الرئيسي لمشروع **PROMANGO**: منصة ويب **عربية أولًا (RTL)** متعددة الشركات لإدارة الشركات والمشاريع والمهام والمهام الفرعية والاعتماديات والتسليم والمراجعة والتدقيق والتقارير. هدف هذه الخطة: **إكمال MVP ثم إطلاقه للعامة** بجودة إنتاجية، مرحلة بعد مرحلة، مع إثبات كل ادعاء بتشغيل فعلي.

مرجع الحقيقة: `PROMANGO_REQUIREMENTS_AR.md` — **لا يُعدَّل أبدًا**. أي تعارض معه يُوثَّق في `docs/decisions.md` ويُرفع للمالك.

## 1. القواعد الثابتة (من المالك)

1. **الوثائق والشرح بالعربية، والكود بالإنجليزية.** رسائل المستخدم النهائية عربية.
2. **لا بيانات وهمية (mock) في الواجهة ولا زر ميت:** كل زر يعمل على API حقيقي، وإلا يُخفى أو يُعطَّل مع سبب مكتوب.
3. **لا أمان في الواجهة وحدها:** كل صلاحية وكل عزل شركات يُفرض في الخادم؛ الواجهة تعكس فقط ما يعيده (`can` و`allowedNext`).
4. **أخطاء واضحة بالعربية:** السبب + طريقة الإصلاح + إعادة المحاولة. الشكل الموحد `{code, message, hint, fields, details}`.
5. **حلقة العمل:** أكمل المهام؛ إن واجهتك مشكلة **اطرحها، ثم اطرح الحل، ثم أصلحها، ثم تابع** المهمة التالية. لا تتوقف لتسأل عمّا له افتراض معقول؛ سجّل الافتراض.
6. **في بداية كل جولة عمل:** أعلن وقت البدء بتوقيت **Asia/Damascus**. استعمل قائمة المهام (TaskCreate/TaskUpdate) ودوّن آخر خطوة «التحقق».
7. **في نهاية كل مرحلة:** حدّث `docs/PROMANGO_progress.xlsx` (بالدرجات الصادقة وسجل جديد وملاحظة)، وحدّث `PROGRESS.md` و`SESSION_HANDOFF.md`، وأرسل للمالك **الملف + نسخة zip** (بلا `.env` ولا `node_modules` ولا `dist` ولا `storage`).
8. **صدق التقارير:** لا تقل «تم» دون تشغيل الأمر. نسبة الإنجاز تُحسب بالصيغة في الملف وتبقى متحفظة (الدرجة تُرفع فقط بدليل). ما لم يُشغَّل يُذكر على أنه لم يُشغَّل.
9. **كلمة مرور بيانات التطوير** (`SEED_PASSWORD`) من البيئة فقط ولا تُكتب في أي ملف. لا تطبع الأسرار (`.env`).
10. **لا تغيّر شيئًا مدمّرًا أو لا رجعة فيه** (حذف بيانات حقيقية، force-push، تغيير أسرار) دون إذن صريح.

## 4. ملاحظات تشغيلية (أخطاء سبق أن أضاعت وقتًا)

- PostgreSQL يتوقف بعد كل إعادة تشغيل للبيئة: `service postgresql start` ثم `pg_isready`.
- npm 10 يفشل (`edgesOut`): استعمل `npx --yes npm@11 install`.
- بناء وتشغيل الخادم يدويًا: `cd apps/api && npm run build && node dist/main.js` (المنفذ 3000). الواجهة: `cd apps/web && npx vite --host 127.0.0.1 --port 5173` ثم `E2E_BASE_URL=http://127.0.0.1:5173`.
- اختبارات الخادم: `npm test` (وحدة) و`npm run test:e2e` (ملف الإعداد `vitest.config.e2e.ts`)؛ قاعدة `*_test` فقط (`resetDb()` يرفض غيرها). `console.log` صامت في vitest — اكتب إلى ملف للتشخيص.
- `UPDATE/DELETE … RETURNING` يعيد `[rows, count]` في TypeORM/pg ← استعمل `rowsOf()` من `src/common/db.ts`. `NOW()` ثابت داخل المعاملة ← `clock_timestamp()` للطوابع المتتابعة. PostgreSQL يرفض معاملات bind غير المستعملة ← ابنِ params لكل استعلام.
- seed: `SEED_PASSWORD=… npm run seed:dev -- --reset` (من `apps/api` بعد `npm run build`). الحسابات: `<exec|pm|spec1|spec2|emp1|emp2>@alpha.test` و`@beta.test`.
- لا `rsync` (استعمل `tar`)، والنسخ الاحتياطي zip يستثني: `node_modules dist storage .env test-results playwright-report .tmp *.log`.
- المالك يعمل غالبًا على Windows: كل خطوة تشغيل يجب أن تكون موثّقة لـ Windows (T9).

## 7. بوابات الإطلاق (كلها شرط، وكل بند بدليل)

1. معايير MVP الـ11 في ورقة «معايير MVP» كلها «مُتحقَّق» (لا «جزئي»).
2. `verify` أخضر في `apps/api` و`apps/web`، وPlaywright الكامل أخضر على السطح والجوال، وCI يشغّلها.
3. اختبارات العزل بين الشركات شاملة لكل مورد جديد، وطفرات (T19) تكتشف إزالة فلتر الشركة والصلاحيات.
4. لا سر في المستودع ولا في سجلات التدقيق؛ الأسرار الإنتاجية مولّدة جديدة ومدوّرة.
5. TLS صالح، رؤوس أمان، CORS مقيّد بنطاق الواجهة، `TRUST_PROXY` صحيح.
6. نسخ احتياطي تلقائي + **استعادة مُجرَّبة** + خطة تراجع للنشر والـ migrations.
7. مسار إنشاء شركة وأول مدير يعمل في الإنتاج (T21)، وكلمات المرور المؤقتة تُعرض مرة واحدة.
8. صفحات الخصوصية/الشروط، وطريقة لتصدير وحذف بيانات شركة.
9. مراقبة وتنبيه أساسيان (توافر، أخطاء 5xx، امتلاء القرص/المرفقات، فشل النسخ الاحتياطي).
10. توثيق تشغيل كامل للمالك (Windows وLinux) ودليل استجابة للحوادث.

## 8. بروتوكول كل جولة عمل

1. أعلن وقت البدء (Asia/Damascus). 2. أنشئ قائمة المهام. 3. شغّل `verify` للتأكد من نقطة البداية. 4. نفّذ بالتتابع، واختبر كل وحدة بالتوازي معها (E2E حقيقي، لا محاكاة للقاعدة/المصادقة)، واكتب طفرة لكل منطق حرج. 5. عند أي مشكلة: **المشكلة ← الحل ← الإصلاح ← المتابعة**. 6. حدّث الوثائق (`decisions` للقرارات، `backlog` للمشاكل، `api-contract §13` لأي انحراف). 7. خطوة أخيرة: تحقّق مستقل (تشغيل كل شيء من جديد)، ثم حدّث ملف التقدم وأرسله مع zip.

## 9. أول ما تفعله الآن

1. أعلن وقت البدء، وأنشئ قائمة المهام.
2. `service postgresql start`، ثم `verify` للجانبين، ثم `seed:dev --reset`.
3. اقرأ `SESSION_HANDOFF.md` و`docs/backlog.md` و`docs/api-contract.md` (§5–§9، §13).
4. أنجز T19+T20.
5. ابدأ **J4** بشاشة المستخدمين على `/users` للمدير التنفيذي: أضف `src/features/users/routes.ts` (يُلتقط تلقائيًا)، مكوّنات القائمة/النموذج/عرض كلمة المرور المؤقتة مرة واحدة مع نسخ، اختبارات مكوّنات + Playwright بالنمط الموجود في `apps/web/e2e`.
6. اسأل المالك **سؤالًا واحدًا فقط** عن القرارات في القسم 5 إن احتجت (ومع الافتراض الموصى به جاهز للمتابعة بدون رد).

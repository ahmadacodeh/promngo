# PROMANGO — SESSION HANDOFF

> ملف تسليم إلزامي بين جلسات Claude Code. الغرض منه أن يستأنف الوكيل العمل من الحالة الفعلية دون إعادة البدء أو اختلاق تقدم.

**آخر تحديث:** 2026-11-07  
**المشروع:** PROMANGO  
**المرحلة المستهدفة:** J — Vue 3 UI + API Integration + UX Motion  
**حالة التنفيذ في مساحة العمل الحالية:** لم يبدأ تنفيذ كود المرحلة J هنا؛ لا يوجد مستودع المشروع البرمجي ضمن الملفات المتاحة حاليًا.

## 2. حقائق لا يجوز تجاوزها

- نظام التطوير المستهدف Windows وPowerShell.
- Node.js ظهر بإصدار `v24.19.0`.
- `npm -v` واجه منع تشغيل `npm.ps1` بسبب Execution Policy.
- `npm.cmd -v` نجح وأظهر `11.17.0`.
- `psql --version` لم يعمل؛ PowerShell قال إن `psql` غير معروف. هذا لا يثبت أن PostgreSQL غير مثبت؛ قد يكون المسار غير مضاف إلى PATH.
- لا توجد نتيجة موثقة تؤكد تشغيل خدمة PostgreSQL أو إنشاء قاعدة البيانات.
- لا توجد نتائج موثقة لاختبارات NestJS أو Vue أو قاعدة البيانات.
- لا تفترض أن المشروع موجود في مجلد Desktop أو أي مسار آخر. اكتشف المسار الفعلي في بيئة Claude Code.
- لا تشغّل SQL الإنشائي على قاعدة تحتوي جداول PROMANGO. استخدم قاعدة جديدة وفارغة فقط، وبعد التحقق من اسمها واتصالها.

## 3. مرجعية المنتج

التقنيات المعتمدة:
- Frontend: Vue 3 + TypeScript.
- Backend: NestJS + TypeScript.
- Database: PostgreSQL.
- API: REST.
- Architecture: Modular Monolith.
- بيئة التطوير: Windows / PowerShell.

الأدوار:
- `EXECUTIVE_MANAGER`
- `PROJECT_MANAGER`
- `SPECIALIZED_MANAGER`
- `EMPLOYEE`

حالات المهام:
- `PLANNED`
- `BLOCKED`
- `ASSIGNED`
- `IN_PROGRESS`
- `SUBMITTED`
- `UNDER_REVIEW`
- `CHANGES_REQUESTED`
- `COMPLETED`

الانتقالات المسموحة:
- `PLANNED → ASSIGNED`
- `PLANNED → BLOCKED`
- `BLOCKED → ASSIGNED`
- `ASSIGNED → IN_PROGRESS`
- `IN_PROGRESS → SUBMITTED`
- `SUBMITTED → UNDER_REVIEW`
- `UNDER_REVIEW → COMPLETED`
- `UNDER_REVIEW → CHANGES_REQUESTED`
- `CHANGES_REQUESTED → IN_PROGRESS`

قواعد إلزامية:
- الموظف لا يعتمد المهمة.
- المراجع المعيّن والمخوّل فقط يعتمد أو يطلب تعديلات.
- سجل المراجعة وتحديث حالة المهمة في transaction واحدة.
- المهمة التابعة تنتظر قبول الاعتماديات السابقة المطلوبة.
- لا تكتمل المهمة الأم قبل قبول كل المهام الفرعية المطلوبة.
- عزل بيانات الشركات يجب أن يُفرض في Backend، وليس بإخفاء عناصر الواجهة.

## 4. الهوية وتجربة الاستخدام

الاتجاه البصري المعتمد:
- Forest Green.
- Emerald Green.
- Mango Orange.
- طابع مؤسسي حديث واحترافي.
- كثافة واجهة متوازنة.
- واجهة عربية RTL افتراضيًا.
- دمج PM في العلامة/الأيقونة بطابع رسمي يوحي بالتطور والتحسن المؤسسي.
- استخدم الخط المحدد في ملف Figma/دليل الهوية بعد التحقق منه؛ لا تخترع خطًا بديلًا إذا كان الخط المعتمد موجودًا.

الحركة والتفاعل:
- انتقالات قصيرة وهادفة بين الصفحات واللوحات.
- Hover/Focus/Pressed واضحة للأزرار والحقول.
- Skeleton loading بدل القفزات المفاجئة.
- Toast أو inline feedback للنجاح والخطأ.
- Validation بجانب الحقل مع وصف كيفية الإصلاح.
- حالات المهام بألوان وأيقونات/نصوص، ولا تعتمد على اللون وحده.
- Motion يحترم `prefers-reduced-motion`.
- تجنب الحركة المستمرة والزخرفة التي تشتت المستخدم.
- لا تستخدم animation لإخفاء بطء أو مشكلة وظيفية.
- اجعل الخطأ واضحًا ومحترمًا وقابلًا للتصرف: ما الذي حدث؟ لماذا؟ كيف أصلحه؟

## 5. المهمة التالية الدقيقة (Next exact action)

**لا تبدأ بكتابة مكونات عشوائية. ابدأ بالاستكشاف والتحقق:**

1. اعرض المسار الحالي ومحتويات مجلد المشروع.
2. نفّذ `git status` إذا كان المجلد Git repository.
3. حدد هل يوجد `apps/web` أو مشروع Vue مستقل، وهل يوجد Backend NestJS.
4. اقرأ `package.json` وملفات router وAPI client وtheme/styles الموجودة.
5. افحص Figma file: الصفحات، Frames، Components، Variables، وأي Prototype links يمكن الوصول إليها. سجّل ما هو موجود فعلًا وما هو ناقص.
6. أنشئ `docs/phase-j-audit.md` يتضمن:
   - جرد الشاشات.
   - ربط كل شاشة بالـ route المقترح/الموجود.
   - المكونات المشتركة.
   - البيانات التي تحتاج API.
   - حالة كل شاشة: موجودة في Figma؟ منفذة في Vue؟ متصلة بالـ API؟ مختبرة؟
   - الفجوات والمخاطر.
7. بعد ذلك قدّم خطة تنفيذ قصيرة مرتبة حسب الاعتماديات، ثم ابدأ بأول شريحة تنفيذية صغيرة.

إذا لم يكن مستودع المشروع موجودًا في بيئة Claude Code، لا تدّع أنك عدّلت ملفات المستخدم. اطلب فتح مجلد المشروع أو توفيره، ويمكنك فقط تجهيز scaffold منفصل إذا وافق المستخدم أو كانت تعليماته تسمح بذلك.

## 7. سياسة الحلقة وإيقاف/استئناف العمل

عند كل دفعة:

`Inspect → Plan → Implement → Test → Diagnose → Fix → Retest → Review → Document`

إذا فشل اختبار:
- لا تتجاوزه.
- اقرأ stack trace ورسالة الخطأ كاملة.
- حدد هل المشكلة في الكود أم البيئة أم البيانات أم إعدادات الاختبار.
- أصلح السبب.
- أعد تشغيل الاختبار الفاشل والاختبارات المرتبطة.
- سجّل النتيجة في `PROGRESS.md`.

إذا انتهت Tokens أو توقفت الجلسة:
- احفظ التغييرات غير المكتملة بشكل آمن.
- حدّث قسم “آخر نقطة وصلنا إليها” أدناه.
- حدّث `PROGRESS.md`.
- لا تدّع أن الجلسة ستعمل في الخلفية أو ستستأنف تلقائيًا.
- في الجلسة الجديدة اقرأ الملفين ثم تحقق من الحالة الفعلية قبل المتابعة.
